# Finance Manager

Веб-приложение для личных и семейных финансов. Реализованы фазы 1–15: основа и регистрация, семьи, счета, доходы и расходы, переводы, месячный бюджет, цели и резервы, их пополнение и снятие, настройки резерва и план накоплений к выбранной дате. Последующие функции реализуются по единой [спецификации](specs/001-finance-manager/spec.md). Обязательные правила — [конституция](.specify/memory/constitution.md).

## Требования

Node.js **24.22.0** (см. `.node-version`), pnpm **12.14.0**, Docker Engine с Compose v2. Все зависимости закреплены в `package.json` и `pnpm-lock.yaml`. `pnpm-workspace.yaml` содержит только настройки установки единственного приложения, дополнительных проектов нет. Разрешены только необходимые build scripts esbuild и unrs-resolver. Skills зависимостей не устанавливаются автоматически.

```sh
npm install --global pnpm@12.14.0
cp .env.example .env
pnpm install --frozen-lockfile
```

Если Docker установлен в `/Applications/Разработка` и команда `docker` недоступна в терминале, добавьте каталог CLI в PATH текущей оболочки:

```sh
export PATH="/Applications/Разработка/Docker.app/Contents/Resources/bin:$PATH"
```

Заполните `.env` перед запуском серверных функций. Для `POSTGRES_PASSWORD` удобно использовать случайную hex-строку: Compose вставляет пароль в URL без дополнительного кодирования. Если используете специальные символы, задайте корректно закодированный `DATABASE_URL` через отдельную настройку Compose. Для каждого из `POSTGRES_PASSWORD`, `BETTER_AUTH_SECRET`, `TOKEN_ENCRYPTION_KEY`, `TRUSTED_PROXY_SECRET` сгенерируйте **отдельное** значение:

```sh
node -e "console.log(require('node:crypto').randomBytes(32).toString('hex'))"
```

Не публикуйте `.env`, дампы БД и вывод секретов. Шаблон `CHANGE_ME` не является рабочим паролем приложения.

## Локальная разработка

```sh
docker compose -f compose.yaml -f compose.dev.yaml up -d db
pnpm db:migrate
pnpm dev
```

Откройте `http://localhost:3000`. `compose.dev.yaml` публикует PostgreSQL **только на 127.0.0.1:5432**. В dev override БД дополнительно подключается к обычной сети `web`, чтобы опубликованный loopback-порт был доступен с хоста; production сохраняет только internal network. Для локальной работы `DATABASE_URL` указывает на localhost, а `APP_ORIGIN` и `BETTER_AUTH_URL` равны `http://localhost:3000`. В production оба URL должны совпадать и использовать HTTPS. База должна быть готова до `db:migrate`; проверить можно командой `docker compose ps`.

При доступе по LAN-адресу (например, `http://192.168.1.51:3000`) задайте **этот же адрес** в `APP_ORIGIN` и `BETTER_AUTH_URL`, затем перезапустите `pnpm dev`. Адрес в браузере должен совпадать с настройками: запросы регистрации с другого origin отклоняются. При успешной регистрации открывается личный кабинет; письмо подтверждения регистрации не отправляется.

Сборка не требует БД и секретов: конфигурация и pool инициализируются при первом серверном обращении. Стартовая страница сообщает о разработке, не показывает вымышленные финансовые данные. Тема следует настройке системы; CSS также поддерживает классы `light`/`dark`.

## Проверки

```sh
pnpm typecheck
pnpm lint
pnpm format:check
pnpm test:unit
pnpm build
pnpm exec playwright install chromium
pnpm test:e2e
```

Playwright самостоятельно запускает dev server на `127.0.0.1:3100`, не использует уже запущенный сервер и проверяет desktop/light и mobile/dark. Сейчас E2E проверяет только каркас и liveness. Mail fixture в `tests/helpers/mail.ts` хранит письма в памяти теста; подключение транспорта приложения к нему выполняется вместе с auth в Фазе 2. Реальные письма в текущих тестах не отправляются.

Интеграционные тесты требуют настоящего PostgreSQL:

```sh
# Задайте отдельный TEST_POSTGRES_PASSWORD в .env и тот же пароль в TEST_DATABASE_URL.
docker compose -f compose.test.yaml up -d --wait
pnpm test:integration
```

Тесты принимают только локальные БД с именем `finance_test` или `finance_test_*`, проверяют отличие от рабочей БД, применяют миграции и не удаляют рабочие таблицы. Тестовый Compose использует отдельный проект и временное хранилище. Не используйте рабочие credentials даже если проверка имени пройдена. Проверки без БД не заменяют интеграционные тесты.

`pnpm format` форматирует исходники и настройки, исключая утверждённые документы Spec Kit. Lint запрещает прямые серверные импорты из Client Components и number-арифметику в финансовом domain и `shared/money`; Next.js `server-only` дополнительно блокирует транзитивный импорт серверных модулей в клиентскую сборку. Календарные и прочие безразмерные операции размещаются отдельно. Эти проверки не заменяют тесты финансовой корректности.

## Миграции

```sh
pnpm db:generate
pnpm db:migrate
```

Schema находится в `src/server/db/schema`, SQL и журнал — в `src/server/db/migrations`. Миграции проверяются перед применением и сохраняются в Git. `0000_bootstrap.sql` инициализирует журнал; миграции `0001`–`0004` добавляют identity/workspace, счета/категории, ledger и security counters. Отложенные ограничения проверяют единственного владельца семьи и согласованность ledger; revisions и аудит неизменяемы. Migration runner сериализует параллельные запуски advisory lock. Не редактируйте уже применённые SQL и не используйте `push` для рабочей БД. Новые изменения — отдельные forward migrations.

`/api/health/live` сообщает о работе процесса; `/api/health/ready` проверяет соединение и полное соответствие записей журнала и SHA-256 SQL текущему выпуску. Без настроек, БД или актуальной схемы ready возвращает 503. Ответы не кешируются и не содержат секретов.

## Self-hosted deployment

Укажите production HTTPS origin, домен и SMTP. Затем:

```sh
docker compose build app migrate
docker compose up -d
```

Порядок: `db healthy` → успешный одноразовый `migrate` → `app healthy` → Caddy. В production наружу опубликованы только порты Caddy. DB находится в отдельной internal network; app и migrate работают от пользователя `node`. Миграционный target содержит инструменты миграций, runtime target — standalone Next.js. Образы Node.js/PostgreSQL/Caddy закреплены тегом patch и manifest digest, их обновление требует явной проверки нового выпуска.

Данные PostgreSQL 18 находятся в volume `postgres_data`, смонтированном в `/var/lib/postgresql`; сертификаты — в `caddy_data`, настройки Caddy — в `caddy_config`. Не выполняйте `docker compose down -v` на рабочем окружении. Не публикуйте app напрямую в обход Caddy. Access log reverse proxy отключён, чтобы auth URL с секретами не записывались в журнал.

## Резервное копирование и восстановление

Дампы хранятся вне публичных volumes, с закрытыми правами доступа. Пример для стандартных `finance` user/database:

```sh
mkdir -p backups
chmod 700 backups
# В текущей оболочке ограничить права создаваемых файлов:
umask 077
docker compose exec -T db pg_dump -U finance -d finance -Fc > backups/finance.dump
docker compose exec -T db createdb -U finance finance_restore_check
docker compose exec -T db pg_restore -U finance -d finance_restore_check --exit-on-error --single-transaction < backups/finance.dump
```

Восстанавливайте в отдельную новую БД. Проверьте журнал миграций и readiness отдельного экземпляра приложения с восстановленной БД. Проверки финансовых остатков и `db:verify-ledger` добавляются в соответствующих фазах; пока команда сверки не реализована. Шифровальные ключи резервируются отдельно от дампа. Расписание, удержание и защищённое хранение задаёт оператор; RPO/RTO не утверждены.

Перед обновлением: дамп, проверка восстановления, репетиция миграций на копии, остановка записей при несовместимых изменениях. Не выполнять автоматические разрушительные down migrations. Команды выше не доказывают восстановимость без фактического пробного восстановления.

## Общая основа Фазы 2

Доступны денежные вычисления со строками и Decimal без скрытого округления, календарные даты с восстановлением исходного дня месяца, схема финансовых данных и общий транзакционный исполнитель команд. Он проверяет доступ, версии и повторные запросы; предупреждение об отрицательном остатке не фиксирует изменения до подтверждения. Чтение нескольких показателей выполняется в согласованном snapshot.

Better Auth работает через защищённый серверный адаптер; прямое управление Organization через публичный endpoint закрыто. Конфиденциальные session tokens шифруются в БД и исключаются из публичных JSON. Callback создания личного пространства выполняется внутри транзакции регистрации; он подключён ко всем успешным signup, включая прямой auth endpoint. Пользователь, credential account, session, профиль и личное пространство фиксируются одной транзакцией.

Сроки приглашений и сброса пароля, лимиты входа, восстановления и приглашений настраиваются серверными переменными из `.env.example`. Caddy заменяет заголовки адреса клиента и доверенного прокси; `TRUSTED_PROXY_SECRET` должен быть отдельным случайным секретом. Прямой доступ к app в production не публикуется.

`MAIL_TRANSPORT=mock` разрешён только вне production и сохраняет сообщения в памяти. Production использует SMTP с TLS/STARTTLS. Playwright требует отдельную `TEST_DATABASE_URL`, автоматически направляет сервер в тестовую БД и запускает приватный SMTP fixture на loopback без реальной доставки. Реальные письма в автоматических проверках не отправляются.

## Регистрация и личное пространство — Фаза 3

Доступны `/register`, `/login`, `/forgot-password`, `/reset-password`, `/profile` и `/dashboard`. Успешная регистрация открывает приватное личное пространство. Better Auth отвечает за пароль, сессию, выход и одноразовую ссылку восстановления; запрос восстановления не сообщает, существует ли почта. После выхода профиль и дашборд перенаправляют на вход.

В профиле изменяются имя, локаль и часовой пояс; почта остаётся неизменной. Сохранение проверяет версию профиля. При конфликте введённые данные остаются в форме, а загрузка актуальной версии требует явного подтверждения. Даты на личном дашборде учитывают сохранённые настройки. Интерфейсы доступны на русском, в обеих темах и с клавиатуры.

Результаты проверок: [US1](specs/001-finance-manager/validation/us01.md). Семейные интерфейсы и счета доступны; доходы доступны на странице счетов; расходы и переводы доступны на странице счетов; дашборд пока показывает личное пространство без финансовых показателей.

## Семьи (Фаза 4)

Раздел `/families` позволяет создать несколько семей, переключать доступное пространство, приглашать участников по почте, отменять приглашения, исключать участников и выходить из семьи. Только владелец меняет название/часовой пояс. Передача владения требует принятия действующим участником; прежний владелец остаётся участником.

Удалить семью может только единственный оставшийся владелец после подтверждения. Финансовые записи сохраняются. В списке удалённых семей ему доступны история и CSV; чужие личные стороны переводов скрыты. Общий импорт/экспорт реализуется последующими фазами. После обновления примените `pnpm db:migrate` для `us02_family.sql`.

Результаты проверок: [validation/us02.md](specs/001-finance-manager/validation/us02.md).

## Счета (Фаза 5)

На `/dashboard` ссылка «Счета личного пространства» открывает `/w/[workspaceId]/accounts`. На странице можно переключаться между доступными личным и семейными пространствами. Все текущие участники семьи могут управлять общими счетами; личные счета доступны только владельцу.

Доступны шесть типов денежных счетов, валюта из поддерживаемого ISO-каталога, описание, нулевой и отрицательный начальный остаток. Денежный ввод — точная строка с десятичной точкой; лишние знаки не округляются. Отображение сумм и дат учитывает локаль профиля. Валюту и пространство существующего счёта изменить нельзя.

Исправление начального остатка требует явного подтверждения и сохраняет автора, время, прежнее и новое значения. При создании или увеличении минуса нужно отдельное подтверждение актуальной версии. Начальный остаток не создаёт доход/расход. Исторические остатки пересчитываются из нового opening и активных записей; сами операции сохраняются. Архив сохраняет средства в общем остатке и историю, исключает счёт из выбора для новых операций, допускает исправление прежних ошибок. Остатки разных валют не складываются.

Новых миграций для этой фазы нет: используется схема foundation. Результаты проверок — [US3](specs/001-finance-manager/validation/us03.md). Доходы доступны в Фазе 6. Расходы и переводы доступны на странице счетов; показатели целей и отчёты реализуются последующими фазами.

## Доходы (Фаза 6)

На странице `/w/[workspaceId]/accounts` форма «Новый доход» позволяет выбрать активный счёт, положительную сумму, финансовую дату, существующую категорию дохода или явно создать новую. Валюта определяется счётом, лишние десятичные знаки отклоняются. Категория, операция, история, аудит, баланс и защита повторной отправки сохраняются атомарно. При ошибке ввод сохраняется; повтор после потери ответа не удваивает доход.

Раздел «Доходы за месяц» считает действующие доходы выбранного месяца отдельно по валютам, без начальных остатков. Остатки, история и доходы страницы читаются из одного snapshot. Дата по умолчанию учитывает часовой пояс профиля для личного пространства и семьи для семейного. Архивные счета и категории недоступны для новых доходов. Результаты проверок — [US4](specs/001-finance-manager/validation/us04.md).

## Расходы и категории (Фаза 7)

На странице счетов доступны расход и управление категориями доходов/расходов: создание, переименование и архивация. Архив сохраняет ссылки и суммы прошлых операций. Расход списывает точную сумму в валюте счёта. При создании или увеличении минуса форма показывает рассчитанный остаток и требует отдельного подтверждения; отмена не меняет данные, устаревшее подтверждение показывает новое предупреждение.

Счета, история, категории и месячные доходы/расходы читаются из одного authorized snapshot. Общая форма использует React Hook Form/Zod, сохраняет ввод при ошибке и предупреждает перед уходом. Новых миграций нет. Проверки — [US5](specs/001-finance-manager/validation/us05.md).

## Переводы (Фаза 8)

На странице счетов форма «Новый перевод» перемещает средства между разными активными счетами одной валюты внутри пространства или между вашим личным пространством и семьёй с действующим членством. Укажите обе точные суммы (они должны совпадать), дату и отдельные описания для пространств отправителя и получателя. Семья видит только свою сторону и её описание. Конвертация валют предусмотрена в US23; редактирование и отмена истории — в US21.

Обе записи, балансы, версии, аудит и receipt сохраняются одной транзакцией. Повтор после потери ответа не списывает деньги снова. Отрицательный остаток требует отдельного подтверждения; изменение балансов делает прежнее подтверждение недействительным. После отзыва членства открытая форма и повторный запрос не дают доступа к семье. Перевод не увеличивает доходы или расходы. Новых миграций нет; используется shared ledger foundation. Проверки: [US6](specs/001-finance-manager/validation/us06.md).

### Использование резерва

На странице «Цели и резервы» у активного резерва доступны расход со связанного счёта и перевод на другой доступный счёт той же валюты. Расход уменьшает общие средства; перевод сохраняет деньги на счёте получателя. После списания пересчитываются накопления, недостающая сумма, покрытие и достижение. Отрицательный остаток требует отдельного подтверждения; при дефиците процент и покрытие не показываются. При нулевом обязательстве резерв сохраняется со статусом «Обязательство отсутствует», дефицит счёта показывается отдельно.

## План накоплений к дате

На странице «Цели и резервы» у каждой активной цели доступен план накоплений. Укажите желаемую дату в настройках цели, дату первого взноса и необязательную ежемесячную сумму. Сервер показывает число оставшихся взносов, рекомендацию с округлением вверх и прогноз; изменения формы имеют предпросмотр до сохранения. Исходное число месяца восстанавливается после коротких месяцев. При редактировании суммы сохранённая исходная дата остаётся прежней, даже если уже прошла; новая дата первого взноса должна быть не раньше сегодня в часовом поясе пространства.

План не создаёт операции и не меняет баланс. Достигнутая цель требует нулевого пополнения; истёкший срок, отсутствие допустимых дат и нулевой план обозначаются явно. Для смены валюты цели с сохранённым планом архивируйте её и создайте новую: сохранённая сумма взноса не конвертируется автоматически. Миграция `us13_savings-plan` применяется обычной командой `pnpm db:migrate`. Проверки фазы — [US13](specs/001-finance-manager/validation/us13.md).

## Переключение пространств (Фаза 16)

Общий переключатель показывает доступные личное и семейные пространства. Переход сохраняет раздел (счета, бюджет или цели), заново проверяет доступ и открывает его без прежних параметров периода и объекта. Название и тип активного пространства видны над финансовыми экранами. Несохранённые формы требуют подтверждения ухода; отмена и ошибка переключения сохраняют ввод. Удалённые семьи доступны удалившему владельцу в группе «только история».

Семейные календарные периоды используют пояс семьи для всех участников. Пояс меняет только владелец с проверкой версии и аудитом; введённые финансовые даты сохраняются. Проверки: [US17](specs/001-finance-manager/validation/us17.md).

## Приватность личных данных (Фаза 17)

Семейное членство и владение семьёй не предоставляют доступа к личным счетам, истории, целям и бюджетам других участников. Прямые ссылки и подмена идентификаторов проходят те же серверные проверки. Семейная сторона перевода скрывает реквизиты и приватное описание личной стороны. После исключения открытая форма и повтор принятой команды не обходят отзыв прав.

На экранах счетов, бюджета и целей отказ показывается без чужих данных; кнопка «Проверить доступ снова» повторно проверяет текущую сессию и права. Последующие отчёты и CSV должны использовать общий серверный guard и scoped projection. Результаты проверок: [US18](specs/001-finance-manager/validation/us18.md).

## Исправление истории и поиск (Фаза 19)

На странице счетов ссылка «История операций» открывает `/w/[workspaceId]/operations`. Даты, счёт, категория и поиск по описанию применяются совместно в активном пространстве. Архивные счета и категории остаются доступны для поиска; удалённые операции помечены и сохраняют историю версий.

Доход и расход можно исправить, изменив сумму, счёт той же валюты, категорию, дату и описание. Перевод исправляется или удаляется целиком. Удаление требует подтверждения; создание или увеличение минуса — отдельного подтверждения актуальных рассчитанных остатков. Балансы, исторические остатки, бюджетные факты и показатели целей читаются с учётом текущих версий; планы сохраняются. Автор создания, автор каждого исправления, время, прежние значения и факт удаления доступны в истории изменений.

Участник семьи может исправлять общие операции независимо от автора. Межпространственный перевод доступен для исправления только владельцу личной стороны при действующем доступе к семье; остальные видят только свою сторону. Переключение пространства сохраняет раздел истории и сбрасывает фильтры. Новых таблиц и миграций нет. Проверки — [US21](specs/001-finance-manager/validation/us21.md).

## Регулярные обязательства (Фаза 20)

Ссылка «Регулярные обязательства» на странице счетов открывает `/w/[workspaceId]/obligations`.
Задайте сумму, счёт, категорию и повторение каждые N дней, недель, месяцев или лет.
Выбранный интервал показывает предстоящие платежи; просроченные видны независимо от него.
План не меняет баланс: расход создаётся только после подтверждения фактических суммы и даты.
Повторное подтверждение не создаёт второй расход; отрицательный остаток требует подтверждения.

Свяжите существующий резерв с ежемесячным обязательством той же валюты. Сумма обязательства
становится источником расчёта цели; накопления сохраняются. Пауза и архив сохраняют историю
и связь. Явный разрыв возвращает ручное управление текущей суммой. Изменение расписания
сохраняет наступившие и оплаченные платежи и пересчитывает будущие неоплаченные.
Главная показывает карточки плановых платежей и просрочки с выбором пространства и интервала.
Миграция `us14_recurring-payments` применяется через `pnpm db:migrate`.
Проверки — [US14](specs/001-finance-manager/validation/us14.md); фаза 18 остаётся незавершённой.
