# Finance Manager Constitution

**Project:** Finance Manager
**Version:** 1.0.0
**Ratified:** 2026-10-17
**Last Amended:** 2026-10-17

## Core Principles

### I. Назначение проекта

1. Приложение представляет собой веб-сервис для управления
   личными и семейными финансами.

2. Приложение должно работать в современных браузерах
   на компьютерах, планшетах и смартфонах.

3. Основной язык пользовательского интерфейса — русский.

4. Основная валюта приложения — российский рубль (RUB).

5. Архитектура должна поддерживать использование
   нескольких валют.

6. На первом этапе приложение разрабатывается
   для личного и семейного использования.

7. Архитектура должна допускать дальнейшее развитие
   в многопользовательский SaaS без необходимости
   полной переработки системы.

8. На начальном этапе запрещено реализовывать
   SaaS-инфраструктуру, биллинг, платные тарифы
   и другие функции, не предусмотренные спецификациями.


### II. Технологический стек

Использование следующего технологического стека обязательно.

**Основные технологии:**

- Language: TypeScript
- Framework: Next.js (App Router)
- UI Framework: React
- Styling: Tailwind CSS
- UI Components: shadcn/ui
- Icons: Lucide React

**Backend и хранение данных:**

- Backend: Next.js Server Actions и Route Handlers
- Database: PostgreSQL
- ORM: Drizzle ORM
- Authentication: Better Auth
- Organizations: Better Auth Organization Plugin
- Validation: Zod
- Financial Calculations: decimal.js

**Frontend-библиотеки:**

- Forms: React Hook Form
- Charts: Recharts
- Tables: TanStack Table

**Инструменты разработки:**

- Package Manager: pnpm
- Unit Testing: Vitest
- E2E Testing: Playwright
- Containerization: Docker
- Deployment: Docker Compose
- Reverse Proxy: Caddy

**Обязательные правила:**

1. Использовать TypeScript в строгом режиме.

2. Использовать стабильные совместимые версии библиотек.

3. Фиксировать версии зависимостей через pnpm-lock.yaml.

4. Не заменять утвержденные технологии альтернативами
   без явного согласования.

5. Не добавлять новые библиотеки, если необходимая
   функциональность уже реализуется существующим стеком.

6. Не использовать экспериментальные возможности
   фреймворков без обоснованной необходимости.


### III. Архитектура приложения

1. Архитектура проекта — Modular Monolith.

2. Frontend и Backend должны находиться
   в одном Next.js-проекте.

3. Приложение должно иметь модульную структуру.

4. Каждый функциональный модуль должен отвечать
   за отдельную предметную область.

5. Бизнес-логика должна быть отделена от:
   - React-компонентов;
   - HTTP-обработчиков;
   - Server Actions;
   - слоя доступа к базе данных.

6. React-компоненты не должны содержать финансовую
   бизнес-логику.

7. Все изменения финансовых данных должны выполняться
   через серверную бизнес-логику.

8. Доступ к базе данных должен осуществляться
   исключительно на сервере.

9. Модули должны взаимодействовать через явно
   определенные интерфейсы.

10. Использовать принципы SOLID, DRY, KISS и YAGNI.

11. Не создавать абстракции без практической необходимости.

12. Не использовать микросервисы, Redis, брокеры сообщений,
    отдельные backend-приложения и другие инфраструктурные
    компоненты без подтвержденной необходимости.

13. Предпочитать простые и поддерживаемые решения
    сложным архитектурным конструкциям.

14. Архитектура должна позволять добавлять функциональность
    без существенной переработки существующих модулей.


### IV. Пользователи и финансовые пространства

Приложение должно использовать модель Multi-tenancy
на основе финансовых пространств (Workspaces).

**Типы пространств:**

1. Personal Workspace
   - Личное финансовое пространство пользователя.
   - Принадлежит одному пользователю.
   - Доступно исключительно владельцу.
   - Содержит личные счета и финансовые операции.
   - Не может быть доступно другим пользователям
     через их участие в семейном пространстве.

2. Family Workspace
   - Общее финансовое пространство семьи.
   - Может включать нескольких пользователей.
   - Содержит общие счета и финансовые операции.
   - Доступ регулируется членством и ролями.
   - Участники имеют доступ только к разрешенным
     данным общего пространства.

**Обязательные правила:**

1. У каждого пользователя должно быть собственное
   личное финансовое пространство.

2. Пользователь может участвовать в нескольких
   семейных пространствах.

3. Семейные пространства должны поддерживать
   приглашение участников.

4. Для управления семейным членством использовать
   Better Auth Organization Plugin.

5. Личные финансовые пространства должны оставаться
   приватными независимо от семейного членства.

6. Семейное пространство не должно автоматически
   получать доступ к личным счетам участников.

7. Каждый счет должен принадлежать ровно одному
   финансовому пространству.

8. Каждая финансовая операция должна иметь
   однозначную принадлежность к финансовому пространству.

9. Финансовые сущности должны быть связаны
   с соответствующим workspace_id.

10. Все запросы к финансовым данным должны
    проверять принадлежность к пространству
    и полномочия текущего пользователя.

11. Нельзя доверять workspace_id, полученному
    от клиента, без серверной проверки прав доступа.

12. Запрещен доступ к данным другого пространства
    без соответствующих полномочий.

13. Запрещено раскрывать личные финансовые данные
    участников в семейной аналитике без их
    явного разрешения.

14. Операции между личными и семейными пространствами
    должны сохранять приватность каждого пространства
    и обеспечивать целостность связанных записей.

15. Модель данных должна допускать добавление
    независимых пользователей и семей при переходе к SaaS.

16. Изоляция финансовых пространств является
    обязательным архитектурным инвариантом.


### V. Финансовые данные и вычисления

Точность финансовых данных имеет высший приоритет.

1. Запрещено использовать JavaScript number
   для денежных вычислений.

2. Для денежных вычислений использовать decimal.js.

3. Для хранения денежных сумм в PostgreSQL
   использовать тип NUMERIC с достаточной точностью.

4. Денежные значения должны передаваться
   без потери точности, например в виде строк.

5. Каждая денежная сумма должна иметь валюту.

6. Использовать стандартизированные коды валют ISO 4217.

7. Правила округления должны быть явно определены
   с учетом конкретной валюты и типа операции.

8. Запрещены неявные преобразования валют.

9. При конвертации валют необходимо сохранять
   использованный курс и параметры конвертации.

10. Финансовые операции должны обеспечивать
    целостность данных.

11. Связанные изменения финансовых данных
    должны выполняться атомарно с использованием
    транзакций PostgreSQL.

12. Не допускается частичное выполнение переводов
    между счетами.

13. Повторная обработка одного финансового действия
    не должна приводить к случайному созданию
    дублирующих операций.

14. Балансы счетов должны быть согласованы
    с историей финансовых операций.

15. Должна сохраняться возможность аудита
    изменений финансовых данных.

16. Запрещено незаметно изменять или уничтожать
    финансовую историю пользователя.

17. Для системных временных меток использовать UTC.

18. При работе с финансовыми датами учитывать
    локальный часовой пояс пользователя.

19. Приоритет корректности финансовых расчетов
    выше приоритета производительности.


### VI. Безопасность и конфиденциальность

1. Для аутентификации использовать Better Auth.

2. Для управления семейным членством использовать
   Better Auth Organization Plugin.

3. Авторизация должна проверяться на сервере.

4. Для операций с финансовыми данными применять
   принцип минимально необходимых полномочий.

5. Отсутствие подтвержденного разрешения должно
   означать запрет доступа.

6. Все входные данные должны проходить
   серверную валидацию через Zod.

7. Не доверять данным, полученным от клиента.

8. Секреты приложения должны храниться
   в серверных переменных окружения или
   защищенном хранилище секретов.

9. Запрещено размещать секреты и приватные ключи
   непосредственно в исходном коде.

10. Запрещено передавать серверные секреты клиенту.

11. Конфиденциальные пользовательские токены,
    которые необходимо хранить постоянно,
    должны храниться в защищенном виде
    с использованием серверного шифрования.

12. Пароли должны обрабатываться только
    через безопасные механизмы Better Auth.

13. Запрещено записывать пароли, токены и секреты в логи.

14. Запрещено раскрывать конфиденциальные финансовые
    данные через сообщения об ошибках.

15. Использовать HTTPS при развертывании приложения.

16. Применять безопасные настройки сессий и cookies.

17. Защищать приложение от распространенных
    веб-уязвимостей согласно рекомендациям OWASP.

18. Финансовые данные не должны передаваться
    сторонним сервисам без явной необходимости
    и соответствующего согласия пользователя.

19. Безопасность пользовательских данных
    имеет приоритет над удобством реализации.


### VII. Пользовательский интерфейс

1. Интерфейс должен быть современным,
   минималистичным и последовательным.

2. Использовать Tailwind CSS и shadcn/ui.

3. Использовать единую дизайн-систему.

4. Поддерживать светлую и темную темы.

5. Интерфейс должен быть адаптивным.

6. Обеспечить полноценное использование
   приложения на мобильных устройствах.

7. Основной язык интерфейса — русский.

8. Форматирование дат, денежных сумм и чисел
   должно учитывать локаль пользователя.

9. Интерфейс должен соответствовать основным
   требованиям доступности WCAG 2.2 AA.

10. Все интерактивные элементы должны иметь
    понятные состояния загрузки и ошибок.

11. Потенциально необратимые действия должны
    требовать подтверждения пользователя.

12. Не допускать незаметной потери введенных данных.

13. Повторно используемые компоненты должны
    размещаться в общей библиотеке компонентов.

14. Не дублировать компоненты с одинаковым назначением
    без обоснованной необходимости.

15. Использовать Recharts для финансовых графиков.

16. Использовать TanStack Table для сложных таблиц.

17. Интерфейс должен четко различать личное
    и семейное финансовые пространства.


### VIII. Качество кода и тестирование

1. Код должен быть читаемым, типизированным
   и поддерживаемым.

2. Использовать единый стиль форматирования.

3. Избегать дублирования бизнес-логики.

4. Не создавать чрезмерно большие компоненты
   и функции.

5. Использовать понятные названия переменных,
   функций, классов и модулей.

6. Не оставлять неиспользуемый код.

7. Не подавлять ошибки без обработки.

8. Для unit-тестирования использовать Vitest.

9. Для end-to-end тестирования использовать Playwright.

10. Все критические финансовые вычисления
    должны покрываться автоматическими тестами.

11. Обязательно тестировать:
    - точность денежных расчетов;
    - округление;
    - операции с разными валютами;
    - переводы между счетами;
    - целостность транзакций;
    - разделение финансовых пространств;
    - права доступа пользователей;
    - невозможность доступа к чужим данным.

12. Исправление ошибки в критической логике
    должно сопровождаться регрессионным тестом.

13. Изменения не должны нарушать существующие тесты.

14. Функциональность не считается завершенной,
    если обязательные проверки не проходят.


### IX. Развертывание и эксплуатация

1. Приложение должно поддерживать self-hosted развертывание.

2. Использовать Docker для контейнеризации.

3. Использовать Docker Compose для управления сервисами.

4. Использовать Caddy в качестве reverse proxy.

5. База данных — PostgreSQL.

6. Конфигурация приложения должна быть отделена
   от исходного кода.

7. Для настройки окружения использовать переменные
   окружения.

8. Файл .env не должен попадать в систему контроля версий.

9. В проекте должен присутствовать .env.example
   без реальных секретов.

10. Должна быть предусмотрена возможность
    резервного копирования базы данных.

11. Должна быть предусмотрена проверяемая процедура
    восстановления данных из резервной копии.

12. Миграции базы данных должны быть версионируемыми.

13. Не допускать потери финансовых данных
    при обновлениях приложения.

14. Базовая работа приложения не должна
    зависеть от обязательных платных облачных сервисов.

15. Не добавлять инфраструктурные компоненты
    без обоснованной необходимости.


## Development Constraints

### Принципы реализации

1. Разработка должна выполняться небольшими,
   логически завершенными этапами.

2. Каждая новая функция должна иметь спецификацию
   с проверяемыми критериями приемки.

3. Не реализовывать функциональность,
   отсутствующую в утвержденной спецификации.

4. Не добавлять дополнительные возможности
   по собственной инициативе.

5. Не переписывать работающий код без необходимости.

6. Перед разработкой проверять существующие
   модули и повторно используемые компоненты.

7. Предпочитать расширение существующей архитектуры
   созданию параллельных реализаций.

8. Не усложнять архитектуру ради гипотетических
   требований будущего SaaS.

9. Сначала обеспечивать корректность,
   затем заниматься оптимизацией.

10. Не принимать архитектурные решения,
    противоречащие данной конституции.


### Документация

1. Поддерживать актуальный README.md.

2. Документировать запуск и настройку приложения.

3. Документировать необходимые переменные окружения.

4. Документировать важные архитектурные решения.

5. Документировать миграции, резервное копирование
   и восстановление данных.

6. Не создавать избыточную документацию,
   дублирующую исходный код.


## Governance

### Приоритет конституции

1. Конституция определяет обязательные правила проекта.

2. Все спецификации, планы реализации и изменения
   исходного кода должны соответствовать конституции.

3. При конфликте между конституцией и техническим
   решением приоритет имеет конституция.

4. AI-агент не имеет права самостоятельно изменять
   утвержденный технологический стек.

5. AI-агент не имеет права самостоятельно менять
   архитектурные принципы проекта.

6. Любые отклонения от конституции должны быть
   явно согласованы с владельцем проекта.

7. Перед реализацией функциональности необходимо
   проверять ее соответствие конституции.

8. Новые функции должны разрабатываться
   через спецификации, а не добавляться
   непосредственно в конституцию.


### Изменение конституции

1. Изменения конституции требуют явного решения
   владельца проекта.

2. Каждое изменение должно сопровождаться
   объяснением причины.

3. Использовать Semantic Versioning:

   - MAJOR: изменение фундаментальных принципов.
   - MINOR: добавление новых обязательных правил.
   - PATCH: уточнение существующих правил.

4. При изменении конституции необходимо проверить
   связанные спецификации и архитектурные решения.

5. Не изменять конституцию автоматически
   ради упрощения реализации конкретной функции.
