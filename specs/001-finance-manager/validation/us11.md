# US11 — Использование резерва

Дата: 17.10.2026. Область: Фаза 13, T091–T096; ФТ-036–039, КУ-008.

## Реализация

- Strict Zod DTO различает расход и перевод, расширяет существующие ledger schemas ссылкой goalId. Суммы — точные decimal-строки; domain расчёты переиспользуют acceptExpense, acceptTransfer и goalProgress.
- Расход выделен в общий executeExpense; обычный расход сохраняет прежний контракт. Резервные расход и перевод используют shared financialTransaction, актуальную авторизацию, workspace/membership/account locks, audit/revisions, balance versions и receipt. В той же транзакции guard проверяет активный reserve, workspace, связанный source account и expectedVersion цели. Версия плана не увеличивается от движения денег.
- Result содержит согласованные goal/account/history и scoped expense/transfer DTO. Повтор operationKey не создаёт второй эффект; изменённый payload конфликтует. Прогресс вычисляется из фактического баланса, отдельные суммы накоплений не хранятся. Новых таблиц и миграций нет.
- На dynamic/no-store странице целей показаны формы использования активного резерва. Переиспользованы React Hook Form/Zod формы с loading/error/focus, dirty guard и подтверждением минуса. Источник перевода предвыбран и зафиксирован. Категории расхода читаются в общем snapshot страницы. Server Action обновляет счета, цели и бюджет затронутых пространств; в React денежной арифметики нет.
- Перевод сохраняет общие средства, расход уменьшает их и увеличивает расходный факт бюджета. Достижение снимается после снижения баланса. При отрицательном балансе percent/coverage null; при нулевом обязательстве remaining=0, reached=null и отдельный признак дефицита счёта.

Unit и PostgreSQL подтверждают 600000−50000→550000, remaining50000, coverage11, reached=false. Обе формы списания дают тот же прогресс; перевод сохраняет общий остаток. Проверены concurrent same-key replay, payload conflict, число scoped audit, отсутствие расходного факта при переводе, unauthorized/foreign goal/account/scope, missing/stale goal version. Ошибка второй leg откатывает balances/versions, ledger/audit и receipt; retry успешен. Negative warning не меняет баланс; подтверждённый расход даёт deficit, null percent/coverage. Нулевое обязательство сохраняет отрицательный баланс с remaining0 и no_obligation; архив блокирует новую запись.

Семейный резерв списывается на собственный личный счёт участника: ответ содержит только семейную leg и общее описание, личный account id и описание получателя скрыты. Исключение участника блокирует повтор и чтение.

Browser US11 проверяет перевод 50000 и 11 месяцев, последующий расход с отдельным negative confirmation до deficit, затем нулевое обязательство с отдельным дефицитом счёта. Проверены отсутствие coverage и горизонтального overflow. Регрессии покрывают обычные расходы, lost-response retry пополнения/перевода, отмену минуса, dirty guard и семейную приватность/отзыв доступа. Mobile/dark screenshot просмотрен. Полный E2E-набор не запускался.

Первоначальный integration запуск был заблокирован sandbox EPERM; после разрешённого запуска вне sandbox обнаружен выключенный тестовый контейнер (ECONNREFUSED). Контейнер запущен, проверки прошли. Дополнительный семейный тест потребовал явного TypeScript-сужения union результата перед обращением к transfer; исправлено, typecheck/build повторены. Финансовая реализация не изменялась из-за этих ошибок окружения и теста.
