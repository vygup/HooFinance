# US10 — Пополнение цели

Дата: 17.10.2026. Область: Фаза 12, T085–T090, ФТ-035–038, КУ-008.

## Реализация

- Strict Zod DTO расширяет существующий контракт перевода ссылкой goalId. Источник и назначение заданы явными workspace/account UUID, суммы остаются decimal-строками. Финансовые вычисления переиспользуют общий transfer domain и goalProgress; новых money/account/goal таблиц, миграций и accumulated balance нет.
- Общий ledger transfer executor выделен из существующего createTransfer без дублирования финансовой логики. Обычный перевод и пополнение используют один financialTransaction, проверку актуального доступа, workspace/membership/account locks, предупреждение отрицательного остатка, saveTransfer, две legs, balance projections, revisions, scoped audit и receipt.
- Дополнительный guard пополнения внутри той же транзакции блокирует и проверяет цель: свой workspace, активность, ожидаемую версию и совпадение связанного счёта с получателем. Устаревшая или перепривязанная цель не может незаметно направить новый перевод прежнему счёту. Версия плана цели не увеличивается от денежного пополнения.
- После записи executor формирует согласованный result: текущие goal/progress, account/balance/history и разрешённая transfer projection. Успешный ответ возвращается после commit. Повтор operationKey возвращает разрешённые views без второго эффекта; другой payload конфликтует. Query читает goal/account/history на одном REPEATABLE READ snapshot. Факт включает действующие revisions истории счёта до и после создания цели.
- Goals page получает funding views в своём snapshot и показывает историю пополнений/списаний. `FundingHistory` переиспользует React Hook Form/Zod TransferForm, фиксирует получателя на счёте цели и предлагает разрешённые счета той же валюты. Сохраняются loading/error/focus, dirty guard, idempotency retry и отдельное подтверждение минуса. Для архивной цели/счёта остаётся история; форма нового пополнения скрыта.
- После ledger commands обновляются страницы счетов и целей соответствующих пространств. Funding action также обновляет бюджет; сам перевод не меняет доходы, расходы и расходный факт бюджета. Даты формы используют пояс личного/семейного пространства. Страницы остаются dynamic/no-store, денежной арифметики в React нет.
- Family result содержит только семейный счёт, цель и семейную transfer leg. Личный account id и приватное описание противоположной стороны не включаются. Отзыв членства блокирует чтение и receipt replay.

## Проверки

Node 24.22.0, pnpm 12.14.0, PostgreSQL 18.6. Использован существующий изолированный контейнер `finance-phase8-tests-db-test-1`, отдельная БД `finance_test`, mock mail. Рабочая БД не использовалась. `/tmp/finance-run` выбирает закреплённый toolchain, `/tmp/finance-test-run` загружает приватный test env.

Unit: перевод 20 000 RUB → actual 240 000, remaining 360 000, progress 40%, coverage 4,8; общий остаток двух счетов остаётся 320 000. Strict DTO, UUID/date/finite positive amounts, same-account, scale и равенство сумм проверены.

PostgreSQL: concurrent same-key/replay, intentional repeat/new key и conflict; ровно две transfer legs и два scoped audit, согласованные server goal/account/history. Пополнение не меняет income/expense fact. Проверены unauthorized/foreign scope/foreign account/foreign goal, связь получателя с целью, archived goal, stale/missing goal version, invalid scale. Ошибка второй leg откатывает первую leg, balances/versions, audit и receipt; retry проходит. Warning минуса ничего не сохраняет, изменение source account требует свежего подтверждения, confirm/replay меняют прогресс один раз. Семейное пополнение из собственного personal account не раскрывает личные детали; исключение участника блокирует read/replay. Полный набор проверяет также прежние FK, financial rollback, revisions, бюджет и цели.

Browser: реальное пополнение резерва с 220 000 на 20 000; показаны 240 000/360 000/40%/4,8 и одна запись transfer_in. После commit ответ намеренно прерывается, повтор сохраняет ровно один перевод. Регрессии общего TransferForm проверяют отрицательный остаток, отмену, dirty guard, personal↔family privacy и открытую форму после отзыва доступа. Reserve regression проверяет изменение платежа, zero/restore/archive. Mobile/dark screenshot просмотрен, горизонтального overflow нет. Это целевая проверка интерфейса; полный E2E-набор в этой фазе не запускался.

Первый unit запуск до реализации ожидаемо падал на отсутствующем domain. Первый integration выявил ошибку тестового helper: undefined expectedVersion подменялся default значением; вызов исправлен, полный прогон прошёл. Первый browser запуск столкнулся с циклическими HMR reload на регистрации. Изначально перенесён основной `.next` (`/private/tmp/finance-phase12-cache-o99z8jv7`), но E2E использует отдельный distDir. После переноса фактического `build/e2e-next` в `/private/tmp/finance-phase12-e2e-cache-i743noq7` чистый browser прогон прошёл. Регистрация и таймауты не изменялись. Production build выполнен вне sandbox из-за служебного порта Turbopack.
