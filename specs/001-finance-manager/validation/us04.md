# US4 — Добавление дохода

Дата: 17.10.2026. Область: Фаза 6, T048–T053, ФТ-021–022,029 и часть КУ-003. Интерфейс — `/w/[workspaceId]/accounts`.

## Реализация

- Строгий Zod DTO: активный счёт, положительная decimal-строка, корректная date-only дата, существующая категория дохода своего пространства или явное создание новой, необязательное описание. Валюта берётся только из счёта, лишние десятичные знаки отклоняются без округления. Domain использует shared Decimal primitives, без React/DB/number arithmetic.
- Общий financialTransaction проверяет session, workspace/membership и account locks, актуальные права, archive status и operation key. Категория и её scoped audit, action, immutable revision/leg, баланс/version счёта, scoped audit дохода и receipt с actionId фиксируются одним commit. Никаких новых таблиц или миграций. Положительный доход улучшает отрицательный остаток и не требует предупреждения об ухудшении минуса.
- Retry с прежним ключом возвращает разрешённую проекцию без повторного эффекта; другой payload даёт conflict; отдельный ключ допускает намеренно одинаковый доход. Отзыв членства запрещает даже receipt retry. Ошибка audit откатывает весь набор, включая новую категорию.
- Доход выбранного месяца учитывает только действующие текущие revisions, отдельно по валютам; opening не является доходом. Границы — первый день включительно, первый день следующего месяца исключительно. Страница получает счета/остатки/историю и месячные суммы из одного authorized repeatable-read snapshot; force-dynamic без shared cache.
- React Hook Form/Zod, русские подписи, pending/error/success, фокус ошибочного поля после снятия pending, сохранение ввода и ключа при ошибке транспорта. Dirty income предупреждает при уходе и смене месяца. Дата по умолчанию использует timezone профиля или семьи; денежные вычисления не выполняются в React.

## Проверенные сценарии

1. 100000 + 20000 = 120000; единичные leg/revision/audit/category/receipt при конкурентном повторе. Отдельная операция с новым ключом увеличивает баланс ещё раз, прежний ключ с другой суммой даёт conflict. Начальный остаток не увеличивает доход выбранного месяца.
2. Ноль/минус/неправильная дата/scale/подмена currency отклонены. Чужой счёт/категория/workspace, категория расхода, архивные счёт/категория и отсутствие session не создают доход. Чтение чужих месячных сумм запрещено.
3. Ошибка вставки income audit откатывает категорию, leg, баланс/version и receipt. Retry после устранения ошибки успешен.
4. Family member добавляет доход на общий счёт. Доход улучшает минус без дополнительного предупреждения. После remove запрещены read и retry; после soft-delete запрещены новые доходы. Личная сторона остаётся приватной.
5. Первый/последний день месяца включены, следующий месяц исключён; RUB/JPY учитываются отдельно, JPY fractional input запрещён.
6. Browser: пустая/ошибочная форма → создание категории → сервер сохраняет доход, но ответ намеренно теряется → ввод сохраняется → retry даёт один доход и 120000 → выбор месяца → повторное использование категории. Скриншоты обеих тем просмотрены, горизонтального overflow нет. Это целевая проверка, не полный аудит WCAG.

Первый unit-запуск до реализации ожидаемо падал на отсутствующем domain. PostgreSQL сначала был недоступен: sandbox EPERM, затем ECONNREFUSED; запущен отдельный тестовый контейнер и проверки выполнены с разрешённым loopback. Browser выявил неявное accessible name категории и ранний фокус на disabled field; исправлены явная подпись и фокус после pending. Тест также дождался загрузки URL выбранного месяца до последующего ввода, устранив гонку полной GET-навигации. В dev server встречается прежнее сообщение `The destination stream errored while writing data`; все финальные assertions прошли, финансовые payload в лог не записываются.

Production build сначала заблокирован sandbox при открытии служебного порта Turbopack; повтор сохранял эту ошибку в кэше. Кэш сохранён во временном каталоге, чистая сборка с разрешённым доступом прошла. Тестовый контейнер остановлен после проверок.
